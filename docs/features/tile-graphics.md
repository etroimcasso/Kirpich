# Tile graphics

The game's graphics, derived from the player's own ROM. The ROM stores four contiguous blocks of
raw Game Boy tile bytes — the font and three screens' worth of tiles; this unit is the table that
names them, the extractor that decodes them, and the PNG files it writes into
`assets/gfx/default/` for the engine to load. It completes the first-start flow: the presence
check and the ROM prompt existed already, and extraction was the missing center.

## Decisions

**Extraction happens in-app, and only in-app.** There is no standalone command-line extractor: the
first-start flow covers players, the development copy script covers developers, and the single
canonical asset path leaves a third tool with no consumer.

**The wrong ROM is refused outright — no header stripping, no fuzzy acceptance.** The gate is
exact size plus SHA-1, checked before a byte is decoded or written. A near-miss ROM would produce
subtly wrong graphics, which is worse than a clear refusal naming the expected ROM. The SHA-1 is
implemented in the port (~a hundred lines) rather than adding a cryptography dependency for one
32 KiB identity check.

**Refuse before writing; rewrite everything.** All four blocks decode in memory before the first
file is written, so no failure leaves a half-populated install. Every run writes all four files —
the flow only reaches extraction when something is missing, and an unconditional rewrite is the
simplest behavior that is honest about what is on disk afterwards.

**The PNG serialization is the port's own, and deliberately minimal.** The engine decodes PNG but
does not encode it, and nothing else in the stack does either. The files are a few KiB, so the
writer uses uncompressed deflate blocks and stays small; correctness is proven by round-tripping
through the engine's decoder, not by matching any other encoder's bytes. Content equality with the
development route is what matters, and the tests prove it through the engine's own loader.

**The fixture pins hashes, never pixels.** A committed pixel array of the decoded graphics would
be ROM-derived content in the repository. The fixture carries each block's dimensions and an
FNV-1a-64 hash of its decoded content — drift detection without committing a single derived pixel.

## Keeping it honest

The extraction table and the fixture are generated by `tools/asm_parser/parse_tile_graphics.py`,
which requires three independent sources to agree before it emits anything: the facts in
upstream's own `dump_gfx.py`, the ROM itself, and the PNGs the disassembly committed. Decoding the
ROM at each recorded (offset, count, format) must reproduce the committed PNG pixel-for-pixel, so
a wrong offset is impossible to transcribe — it cannot produce the reference pixels. See
[`../engine/tile-graphics.md`](../engine/tile-graphics.md) for regeneration.
